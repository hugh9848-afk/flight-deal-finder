기존 앱을 개선하는 방향이 타당합니다. 첨부 문서의 실험은 유용했지만, 검색 결과를 실제 여행 조건과 연결하는 코드에 결함이 남아 있었습니다. 새 앱을 만든다고 공급자의 커버리지와 호출 한계가 없어지지는 않습니다. 이번에는 기존 구조를 유지하면서 예산 관리, 귀국편 확인, 아프리카 직접 조회와 알림 흐름을 수정했습니다.

- 새 인수인계 문서와 SerpApi 1차 실험 결과, 실제 소스, 테스트, 자동 실행 설정을 대조했습니다. 문서의 설명은 검증 대상으로 읽었습니다.

**1. 가장 중요한 발견: 현지 귀국 출발일은 인천 도착일이 아닙니다.**

실제 SerpApi 응답으로 확인한 결과입니다. 예시는 현재 구매를 보장하는 제안이 아니라 코드 검증에 사용한 조회 결과입니다.

| 항목 | 확인 결과 |
|---|---|
| 인천 출발 | 2027-01-16 |
| 파리 귀국 출발 | 2027-01-30 |
| 왕복 조회가 | 790,500원 |
| 실제 인천 도착 | **2027-02-01 10:30** |
| 기존 방식의 여행 일수 | 15일 |
| 실제 출국~인천 도착 달력 일수 | **17일** |
| 경유 | 출국 1회, 귀국 1회 |

Google Flights 첫 응답에 왕복 가격이 있어도 `flights`에는 출국편만 있습니다. 귀국편은 출국편의 `departure_token`을 전달해 추가 조회해야 합니다. 이는 [SerpApi 공식 Flights 문서](https://serpapi.com/google-flights-api)의 동작과 실제 응답 모두에서 확인했습니다.

수정 후에는 출국편 목록에서 저렴한 유효 출국편 하나를 선택하고, 그 출국편에 연결된 귀국편 목록을 조회합니다. 귀국 응답의 가격을 왕복 총액으로 사용하며 두 가격을 더하지 않습니다. 실제 귀국 구간에서 ICN 도착 공항과 도착 날짜를 읽어 여행 일수를 다시 계산합니다. 현지 귀국 출발이 20일째라도 인천 도착이 21일째라면 범위 밖으로 표시하고 알림에서 제외합니다.

귀국 조회가 실패하거나 토큰이 없으면 출국편과 조회 가격은 남기되 귀국편은 미확인으로 유지합니다. 실제 공항이 GMP로 확인된 후보는 ICN 전용 결과에서 제외합니다.

**2. 아프리카 직접 조회와 예산 배분을 실제 스캔에 연결했습니다.**

기존 `splitDetailBudget()`은 테스트에서는 작동했지만 스캔에서 호출되지 않았습니다. 또한 가격 없는 아프리카 도시는 기존 후보 목록에 없으므로 후보 순서만 나눠서는 조회할 수 없었습니다.

이를 실제 검색 계획을 만드는 코드로 교체했습니다. 아프리카에서 캐시 가격이 없는 도시를 골라 출발일과 여행 기간을 순환하며 직접 조회합니다. 이때 만드는 것은 검색 조건이며, 가짜 가격이나 특가 후보를 생성하지 않습니다. 넓은 검색 결과가 전부 비어 있어도 직접 조회를 진행할 수 있습니다.

기본 예산은 다음과 같습니다.

| 용도 | 검색 요청 상한 |
|---|---:|
| Explore·Deals 발굴 | 5회 |
| 상위 후보 4개 일정의 출국·귀국 조회 | 8회 |
| 캐시가 빈 아프리카 2개 일정의 출국·귀국 조회 | 4회 |
| 합계 | **17회/실행** |

일정당 최대 2회이므로 상세 조회 12회로 최대 6개 일정을 조회합니다. 작은 정수 예산이라 70:30의 목표 비율은 4:2, 즉 약 67:33으로 배분됩니다. 빈 아프리카 도시가 부족하면 다른 후보로 채웁니다. 같은 노선·출발일·귀국일의 중복 조회는 줄였습니다.

발굴에서는 요청한 지역들을 한 번씩 살펴본 뒤 두 번째 기간을 조회하도록 바꾸고, Deals 1회를 먼저 확보합니다. 예산상 Explore 기간 하나만 볼 수 있는 경우에는 1주와 2주 조건을 주기적으로 바꿉니다. 지역 선택도 실제 공급자에 전달합니다.

이 변경은 탐색 기회를 확보한 것입니다. 아프리카 특가 수가 얼마나 증가하는지는 앞으로 운영 결과로 측정해야 합니다. 이번 실제 API 검증 대상은 파리 왕복 한 일정이며, 아프리카 개선 효과를 실측했다고 주장하지 않습니다.

**3. 예산 관리의 남은 결함을 수정했습니다.**

기존 코드는 월 장부와 이번 실행 예약 수를 더해 같은 호출을 중복 계산했습니다. 또 장부 저장은 네트워크 호출 후였으며, 손상된 장부를 새 장부로 취급하고 자동 실행에서는 장부 파일을 저장소에 남기지 않았습니다.

수정 사항:

- 검색 전에 사용 예약을 파일에 기록합니다. 기록에 실패하면 실제 검색을 시작하지 않습니다.
- 손상된 장부를 0회로 초기화하지 않고 중단합니다.
- 파일 잠금과 임시 파일 교체로 같은 장부에 대한 동시 기록 충돌을 막습니다. 남아 있는 잠금 파일은 자동 삭제하지 않고 검색을 멈춥니다.
- 월 장부는 한 번만 계산합니다. 계정의 실제 사용량도 자체 월 상한과 대조합니다.
- 응답 본문 수신까지 시간 제한을 적용합니다. 헤더만 도착하고 본문이 멈추는 경우도 종료합니다.
- 인증·권한·호출량 오류와 잘못된 예산 설정은 중단 사유로 처리합니다.
- 자동 실행은 실패 후에도 사용 장부 저장을 시도하도록 변경했습니다. 저장소 쓰기가 실패하면 장부 영속화까지 보장되지는 않지만, 다음 실행의 계정 사용량 확인도 별도로 적용됩니다.

무료 캐시 응답이나 실패 요청도 로컬 장부에서는 보수적으로 한 번 사용한 것으로 셉니다. 따라서 로컬 장부 숫자와 SerpApi 대시보드 숫자는 다를 수 있습니다. 월 200회 자체 상한은 유지했습니다.

**4. 더 싼 후보와 다른 귀국일이 사라지는 문제를 수정했습니다.**

기존 상세 조회 대체 기준은 사실상 ‘도시+출발일’이었습니다. 한 일정을 조회하면 같은 도시에서 같은 날 출발하지만 귀국일이 다른 참고가까지 지웠습니다. 이후 중복 정리도 같은 주차·가격대 후보를 여행가치 점수로 합쳐 더 싼 운임을 잃을 수 있었습니다.

실제 스캔에서는 출처, 양쪽 일정, 가격, 항공편이 같은 결과만 중복 처리하도록 바꿨습니다. 다른 귀국일, 다른 가격, 다른 공급자의 할인 근거는 남습니다. 조회 실패 시에도 기존 참고가는 유지합니다. 출국편만 확인한 후보와 귀국편까지 확인한 후보가 함께 보일 수 있는데, 이는 서로 확인한 정보 수준이 다르기 때문입니다.

순위는 유효 기간 안의 후보를 먼저 두고, 노선 가격 비교로 계산한 할인율을 우선하도록 바꿨습니다. 여행가치 점수는 그 다음 기준입니다. 같은 스캔의 다른 도시들과 비교한 비율은 실제 과거 대비 할인율처럼 취급하지 않습니다. 화면에서도 ‘평소보다’ 대신 비교 기준을 구분하고, 기준가보다 비싼 경우 ‘음수 할인’이 아니라 ‘높음’으로 표시합니다.

**5. 복합 공급자에서 꺼져 있던 알림 흐름을 복구했습니다.**

기존 복합 공급자 경로는 `confirmed`인 특가만 알렸습니다. 현재 SerpApi와 Travelpayouts 모두 최종 가격 확정을 지원하지 않으므로, 이 경로에서는 특가를 찾아도 알림이 발생하지 않았습니다.

이제 미확정 특가도 알림 대상으로 검토하지만 다음 조건을 확인합니다.

- 실제 출국 공항과 귀국 도착 공항이 모두 ICN으로 확인됨.
- 실제 인천 도착 날짜로 여행 기간을 계산했고 5~20일 안에 들어감.
- 가격 충돌이 없고 기존 할인 기준을 충족함.
- 자체 이력·Google 제공 할인은 기존 신뢰도 조건 적용. Google 이력으로 앱이 계산한 할인은 이력 5개 이상과 양방향 확인을 요구하며, ‘앱 계산’과 판정 신뢰도를 그대로 표시함.
- 같은 스캔의 상대 비교만으로는 미확정 특가 알림을 보내지 않음.

Travelpayouts 참고가만 있고 귀국편을 모르는 경우에는 목록과 상세 조회 후보로 유지하지만 알리지 않습니다. 즉, 알림이 많이 오도록 조건을 풀기보다 실제 여행 조건을 확인한 후보가 알림으로 연결되게 했습니다. 이번 작업에서 실제 웹훅 전송이나 GitHub 이슈 생성은 하지 않았습니다.

화면의 귀국 공항 미확인 배지, 공급자별 확인 링크 설명, 아프리카 지역 분류도 함께 보완했습니다.

**솔직하게 남는 한계와 다음 판단 기준**

1. 월 250회 무료 검색으로 유럽·아프리카 전체의 모든 날짜와 5~20일 조합을 계속 감시할 수는 없습니다. 현재는 넓은 발굴과 일부 상세 검증을 결합한 표본 탐색입니다.
2. 상세 조회에서는 저렴한 출국편 하나에 연결되는 귀국편을 확인합니다. 모든 출국편과 모든 귀국편의 조합에서 전역 최저가를 증명하지는 않습니다.
3. 오픈조는 아직 SerpApi 실제 검색에 구현되어 있지 않습니다. 현재 지원하는 것처럼 표시하지 않았습니다. 귀국편과 예산 검증을 안정화한 뒤 별도의 소량 실험으로 추가하는 것이 다음 순서입니다.
4. 판매 화면 재확인, 수하물·환불조건, 일정 시간이 지난 뒤 가격 재현성은 여전히 별도 확인이 필요합니다. 이번 790,500원도 구매 확정 가격이 아닙니다.
5. 자체 이력은 아직 짧고 기간·계절·조회 조건이 섞일 수 있습니다. 관측이 쌓인다는 사실만으로 정확한 할인율이 보장되지는 않습니다. Google 이력 중앙값도 Google이 직접 제공한 할인율과 다릅니다.
6. ‘14일 A/B 실험이 진행 중’이라는 문서 표현만으로 성능 개선이 증명되지는 않습니다. 앞으로는 추가로 발견한 목적지 수, 양방향 확인 성공률, 아프리카 직접 조회 성공률, 30분 뒤 가격 재현율, 유효 특가 한 건당 호출 수를 기록해 유료 결제 여부를 판단하는 것이 좋습니다. 이번에 별도 A/B 자동화는 만들지 않았습니다.

**다음 작업자에게 전달할 내용**

현재 로컬 변경을 먼저 검토한 후 `npm test`를 실행하고 커밋·푸시하면 됩니다. 테스트를 위해 기존 코드에서 다시 구현할 필요는 없습니다. 자동 실행 기본 사용량은 여전히 발굴 5회+상세 12회입니다. 다만 상세 12회는 12개 일정이 아니라 최대 6개 일정의 출국·귀국 확인이라는 점을 유지해야 합니다.
